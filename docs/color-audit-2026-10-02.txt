FWB website and mobile web color audit — October 2, 2026

Decision applied in this update
Dark green is the main surface and action color. Neon green is limited to borders,
small icons/badges, completion markers, and focus indicators. Text on main actions
is warm white. Logged sets/rounds remain #0B1811, with neon state cues.

Scope and method
- Scanned all 21 production root HTML entry pages, shared CSS, and the five hosted
  assistant/consent template mirrors. All 26 templates load the dark theme last.
- Inspected public entry screens at 390px and 1280px, including homepage Training,
  Results, and Start panels; signup/invite/conversion forms; support/privacy/terms;
  consent; and client/coach sign-in.
- Inspected the authenticated client's Home, Workouts, Logs, Progress, Settings,
  Stats, and Nutrition panels at 390px before the coach access redirect.
- Checked completed logging, recommendation, trash/video, and sharing styles in
  representative component fixtures using the production stylesheets. No real
  workouts were logged, copied, skipped, saved, or deleted to test these states.
- Checked 32 representative action classes and nested labels in a component
  fixture. Main actions use dark surfaces; small video icons retain a neon fill.
- Coach Admin, Session Logger, and Exercise Library protected runtime screens
  require coach sign-in. Reviewed their source and representative shared component
  styles; did not verify authenticated coach flows end to end.
- Native SwiftUI apps, email templates, and old design mockups are outside this
  website/mobile web audit. Images' own pixels and native checkbox fill declarations
  are not counted as confirmed page-surface bugs.
- Contrast readings are diagnostics from computed solid colors. Gradients,
  transparent layers, animations, and platform controls need visual judgment.

Requested fixes included
- Client dock: Home, Workouts, Logs, Progress, Settings. Messages is at the upper
  left of Workouts; Stats and Nutrition open from Settings and have a back button.
- Settings stays reachable in Coach Client View for Stats/Nutrition, while private
  notification shortcuts remain unavailable in that preview.
- Progress personal-best panel, stacked deck layers, comparison arrows, neutral/
  positive/negative badges, and monthly report link use readable dark colors.
- Stats DEXA upload/review/archive panels, native file picker text, privacy link,
  metric tabs/graph line, photo gallery/history surfaces use the dark palette.
- Recommended exercise suggestions retain readable nested text. Trash controls
  use coral on a dark reminder surface. Video fallback uses an SVG instead of emoji.
- Logged set/round rows and legacy completed exercise/group decks stay dark.
- Share workout and other primary actions use dark green with neon outlines.
- Relevant CSS/JS asset URLs are versioned for existing installations.

Underlying cause and recommended follow-up
The source scan found 574 legacy light-fill/dark-ink rule candidates across 20 CSS
files. This is NOT 574 confirmed bugs: many are already overridden by the shared
bridge, intentional image/medal styles, or state-specific rules.
The recurring cause is mixing literal colors and --black/--white aliases with
semantic dark-theme roles. A parent dark surface does not repair explicit black
child text, and a default-state bridge does not always cover selected/completed/
hover/disabled states. Replace those component rules with semantic surface, ink,
muted, accent, and danger tokens, then verify the state matrix at mobile/desktop.

Validation and limits
128 targeted Node checks passed, covering navigation/routing, Settings, dock
mounting/focus, Progress records, DEXA import behavior, messages, exercise media,
account settings, and sharing. Browser checks used production CSS and actual
public/client panels where access was available; completion/sharing contrast
checks used sample component fixtures. These checks are not a claim that every
protected coach screen, modal, or native app has passed a full visual audit.
The coach redirect signed out the local preview session; client sign-in is needed
again to continue authenticated browser verification. No credentials or private
measurement values are included in this report.
